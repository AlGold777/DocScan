## 4. Требования к геометрии камеры — DM-01

### Проблема

Сейчас живая рамка нормализуется относительно полного буфера `ImageAnalysis`. При переносе на снимок применяется только `rotateNormalizedQuad`. При общем `ViewPort` файл от `ImageCapture` может уже содержать обрезку по области просмотра. Поэтому одинаковые нормализованные числа обозначают разные физические точки.

Это поведение CameraX описано в [ViewPort API](https://developer.android.com/reference/androidx/camera/core/ViewPort): область анализа задаётся метаданными crop rect, а при записи фотографии в файл CameraX применяет соответствующую обрезку.

### Требуемое решение

1. Явно раздели пространства координат:
   - полный буфер анализа;
   - его `cropRect` и поворот;
   - область просмотра PreviewView;
   - фактически сохранённый JPEG;
   - ориентированное изображение после EXIF;
   - уменьшенная копия для детектора.
2. Реализуй и протестируй преобразования между ними. Перенос рамки анализа в JPEG не может состоять только из поворота и независимого деления x/y на размеры буфера.
3. Используй метаданные CameraX и проверяемые матрицы преобразования. Можно применять `OutputTransform`, `CoordinateTransform`, `ImageProxyTransformFactory` и подходящую геометрию файла, если их контракт соответствует реальным данным текущей версии CameraX.
4. Простое включение `isUsingCropRect = true` без проверки того, относительно какого начала отсчёта поступают точки, не считается исправлением.
5. При неизвестном преобразовании не используй жёстко заданные поправки под один телефон. Отключи сравнение с живой рамкой для этого снимка; детекция по самому JPEG остаётся доступной.
6. EXIF-поворот/отражение применяется ровно один раз. Размеры и точки после него должны описывать одно пространство.
7. Корректно обрабатывай 0/90/180/270°, ненулевое начало `cropRect`, различные разрешения анализа и JPEG, портретный и альбомный PreviewView, `FILL_CENTER`.
8. Обновление размеров PreviewView, ориентации или конфигурации камеры создаёт новое поколение геометрии. Старая рамка не переносится в новую конфигурацию.

### Контрольный пример

Буфер анализа 1280×960, `cropRect = (160, 0, 1120, 960)`, без поворота. Точка полного буфера `(320, 240)` после обрезки и нормализации становится `(1/6, 1/4)`, а не `(1/4, 1/4)`. Этот пример обязан быть отдельным тестом. Дополнительно нужны двусторонние преобразования с поворотами и разным масштабом JPEG.

Критерий: на синтетических матрицах ошибка преобразования и обратного преобразования не больше 1 пикселя исходного изображения; для нормализованных вычислений до округления — не больше `1e-5`. Не оценивай правильность только визуально на одном экране.

## 5. Единое состояние живой рамки — DM-02

### Проблема

Сейчас `quadForCapture` получает сырой кандидат до временной фильтрации. На экране показывается другой, сглаженный контур. У состояния нет времени кадра и поколения сессии. При отказе детекции JPEG живая рамка используется как запасная геометрия обрезки.

### Требуемый контракт

Введи одно неизменяемое опубликованное состояние детекции. Конкретные имена выбирай по стилю проекта, но состояние должно содержать:

- идентификатор поколения камеры/геометрии;
- геометрию источника или ссылку на неизменяемое описание преобразования;
- контур в явно названном пространстве;
- исходный score, не выдаваемый за калиброванную вероятность;
- время получения кадра анализатором в монотонных часах;
- статус подтверждения и пригодность для отображения/согласования;
- при необходимости время окончания обработки отдельно от времени получения.

Не сравнивай sensor timestamp с `elapsedRealtime` без доказанного единого timebase. Для возраста состояния используй согласованные монотонные часы; wall clock не подходит.

### Поведение

1. Начальный или резко изменившийся кандидат не становится зелёной подтверждённой рамкой после одного кадра. Требуется как минимум два последовательных согласованных наблюдения.
2. Сохранить разумное EMA-сглаживание можно, но сглаживание выполняется в согласованном пространстве источника. Экранная рамка — проекция опубликованного контура, а не самостоятельное состояние.
3. Возраст пригодного состояния ограничь именованной настройкой. Начальное значение — 300 мс при текущей частоте анализа около 10 Гц. Значение разрешается изменить по измерениям с объяснением.
4. Удерживаемая после пропуска рамка не выглядит как подтверждение нового кадра: допускается краткое приглушённое отображение. После срока годности она не участвует в согласовании/обрезке.
5. Ошибка анализа, потеря камеры, остановка/возобновление сессии и смена геометрии инвалидируют пригодность старого состояния.
6. При нажатии затвора захватывается одна согласованная копия состояния. Поздние кадры не меняют уже начатую операцию.
7. UI-обновление от старого поколения игнорируется даже после быстрого выключения/включения режима.

### Обязательная политика сохранённого снимка

Автообрезка разрешается по валидированному кандидату, найденному **на самом сохранённом JPEG**. Живой контур используется для подсказки, согласования и при необходимости выбора области поиска.

Если детектор JPEG не нашёл надёжную геометрию, сохраняй необрезанный снимок. Не возвращай прежний путь `stillQuad ?: capturedQuad`, который автоматически применяет непроверенную геометрию другого кадра.

Если свежая, подтверждённая и корректно преобразованная живая рамка есть, а кандидат JPEG существенно ей противоречит, сохраняй исходник без автоматического warp. Если живой рамки нет или её преобразование неизвестно, хороший кандидат самого JPEG может использоваться самостоятельно.

Проверка согласия должна учитывать максимальную ошибку отдельных углов, а не только среднюю ошибку по кадру. Сравнивай геометрию в одном пространстве; сопоставляй углы без ложного расхождения из-за циклической перенумерации. Допуски привязывай к размеру документа. Начальный ориентир: максимальное смещение угла до 6% диагонали документа и polygon IoU не ниже 0.8; окончательные пороги обоснуй положительными и отрицательными примерами.

Порог 0.12 нормализованного кадра не переносить механически: у небольшого документа он допускает слишком большую относительную ошибку. При отказе сообщай понятный результат, например: «Снимок сохранён без обрезки: границы не подтверждены». Не выдавай отказ за успешное выравнивание.

## 6. Владение состоянием и потоки — DM-03

1. У временного фильтра и состояния детекции должен быть один поток-владелец либо эквивалентный последовательный механизм обработки событий.
2. `update`, `onMissing`, `reset`, переключение режима и смена поколения должны иметь определённый порядок. Текущая смесь вызовов из анализатора и UI недопустима.
3. Предпочтительно: анализатор последовательно обрабатывает события, UI получает неизменяемые результаты. Переключение режима инвалидирует поколение сразу, а сброс внутреннего фильтра доставляется владельцу упорядоченно.
4. Публикация между потоками должна обеспечивать видимость и целостность состояния. Одного `@Volatile` у ссылки на quad недостаточно для остальных изменяемых полей фильтра.
5. Не блокируй главный поток ожиданием анализатора, OCR, допуска памяти или завершения старой сессии.
6. `ImageProxy` закрывается ровно один раз при успехе, пропуске кадра и исключении. Не сохраняй ссылку на его буфер для использования после закрытия.
7. После уничтожения Activity нет позднего рисования в её View и использования освобождённых bitmap.

Приёмка: детерминированные тесты с управляемыми очередями событий воспроизводят старое обновление после выключения режима, два переключения подряд, пропуски, ошибку, большой скачок и изменение геометрии. Старая рамка не «воскресает». Не используй flaky stress-тест как единственное доказательство.

## 7. Память и тяжёлая обработка — DM-04

### Цель

Учитывать реальные одновременно живущие буферы и не запускать тяжёлое выравнивание бесконтрольно параллельно с OCR/импортом. При этом не блокировать аппаратный спуск и запись JPEG общей очередью тяжёлых задач.

### Требования

1. Раздели получение/надёжную запись JPEG и последующее вычисление производной страницы. Общий допуск применяется к обработке после получения снимка, а не к вызову CameraX shutter.
2. Используй существующий `HeavyWorkScheduler` либо минимальное совместимое расширение. Не создавай независимый лимитер, который не знает об OCR и импорте.
3. Убери постоянные 80 МиБ как оценку для любых размеров. Оценивай конкретную операцию: декодированный bitmap, полноразмерный исходный Mat, warp Mat, выходной bitmap, память детектора/служебный резерв. Учитывай реальное время жизни буферов.
4. Расчёт делай в `Long`, с защитой от переполнения и некорректных размеров. Для теста полного ARGB-прохода четыре изображения 4000×3000 — уже примерно 192 МБ в десятичном представлении, без прочей памяти процесса. Не резервируй для такого пути 80 МиБ.
5. Не увеличивай общий бюджет 96 МиБ произвольно ради прохождения допуска. Сначала уменьшай число одновременно живущих буферов или выбирай рабочее разрешение, помещающееся в согласованный бюджет. Больший лимит допустим только после измерений и документированного обоснования для профиля устройства.
6. Детекция должна получать маленькую копию без предварительного создания полноразмерного RGBA Mat только ради последующего уменьшения до 720 px. Полноразмерный источник нужен на стадии warp, а не для поиска контура.
7. Полный исходный JPEG сохраняется независимо от выбранного рабочего разрешения. Не обещай warp 12 Мп на каждом устройстве и не уменьшай исходный файл ради экономии памяти.
8. Буферы, Mats, итераторы и временные файлы освобождаются при успехе, исключении, отмене и закрытии UI. Операция не удерживает разрешение scheduler после завершения.
9. Недостаток памяти при автообрезке не уничтожает снимок: сохраняется оригинал, UI сообщает об отсутствии выравнивания. В ручном редакторе сохраняется текущая версия страницы и возможность повторить действие.
10. Проверь, что новая очередь не создаёт deadlock: задача не должна ждать OCR/IO, которому для завершения нужен занятый ею executor или допуск.

### Измерения

Запиши размеры входа/выхода, расчёт резерва, длительность, выборочный пик PSS и параметры устройства. PSS всего процесса не равен бюджету bitmap и не должен объявляться его точным измерением.

Нужны одиночная съёмка, серия из 10 снимков с работающим OCR и повторная автообрезка большого изображения. На эмуляторе допустимо проверять очередь/освобождение и измерять свой PSS; это не доказательство поведения физической камеры. При отсутствии телефона аппаратный сценарий остаётся явно непроверенным.

## 8. Подтверждение автообрезки в редакторе — DM-05

### Проблема

`createDocumentCropPreview` и `applyDocumentCrop` независимо запускают детекцию на разном разрешении. Пользователь подтверждает один результат, а примениться может другой.

### Требуемое решение

Верни из построения превью неизменяемый план обрезки. Он должен содержать:

- `pageId`, исходный `imageVersionId` и необходимые признаки актуальности;
- идентичность исходного артефакта;
- размеры ориентированного изображения;
- утверждённый четырёхугольник в нормализованных координатах этого изображения;
- сведения об ориентации/преобразовании, достаточные для одинакового применения;
- при необходимости параметры результата и версию алгоритма.

План и bitmap превью должны соответствовать одной геометрии. Конкретное имя, например `DocumentCropPlan`, не является обязательным.

1. Нажатие «Применить» использует утверждённый план и качественный источник. Повторная детекция в этом пути запрещена.
2. Освобождение bitmap при закрытии диалога не уничтожает данные плана до завершения запущенной операции.
3. Перед коммитом проверь актуальность исходной версии страницы через действующие механизмы хранилища. Если страницу пересняли, заменили, повернули или удалили, старый план отклоняется с понятным сообщением.
4. Новое изображение создаёт новую версию; результат не записывается поверх исходного артефакта.
5. Отмена и неудачное применение не меняют текущую версию и OCR страницы.
6. После успешной замены старый OCR не считается результатом новой версии. Используй существующую политику ReOCR, не меняй её побочно для других редакторов.

Приёмка: детектор можно заменить тестовым источником, который при втором вызове вернул бы другой объект. Превью получает первый контур, применение использует его же; второго вызова детектора нет. Отдельно проверь устаревание плана и отмену.

## 9. Восстановление режима и интерфейс — DM-06

1. Включённый/выключенный режим сохраняется при обычном повороте телефона и пересоздании Activity. Сохраняется пользовательский выбор, а не старые координаты рамки.
2. После пересоздания камеры рамка подтверждается заново в новом поколении. Ни quad, ни матрица прежнего PreviewView не восстанавливаются как пригодные для нового снимка.
3. Используй `SavedState`/`onSaveInstanceState` или существующий подход проекта. Для обычного нового запуска можно оставить прежний default; не вводи постоянную настройку между запусками без необходимости.
4. Состояние кнопки должно быть доступно не только по цвету: `selected`/`checked`, понятное описание или `stateDescription`. TalkBack различает включённый и выключенный режим.
5. Сохрани текущий дизайн интерфейса; не отменяй незакоммиченные изменения внешнего вида кнопок.
6. Статусы различают: документ выровнен; снимок сохранён без обрезки; обработка не удалась, оригинал сохранён; ручное применение отменено/план устарел.
7. Не показывай пользователю названия внутренних DTO, PSM, матриц и scheduler. Новые строки добавляй в ресурсы с соблюдением имеющейся локализации.

Приёмка: включить режим → `ActivityScenario.recreate()` → режим включён, старой рамки нет. Для исходно выключенного режима результат аналогично остаётся выключенным. Проверить доступное состояние кнопки и возврат из background.

## 10. Детектор обычных страниц и длинных чеков — DM-07

Текущее ограничение aspect > 3.3 отбрасывает правильные контуры длинных чеков. В рамках этой работы поддержи прямые плоские чеки с отношением сторон до 1:12, если весь документ виден и разрешения хватает для поиска границ.

1. Не исправляй проблему одной заменой 3.3 на 12. Пересмотри минимальную площадь, короткую сторону, морфологические ядра и штраф aspect согласованно. Иначе полный чек продолжит отсеиваться или начнут выбираться полосы текста.
2. Допускается внутренняя отдельная оценка кандидатов «страница»/«чек», без дополнительного переключателя для пользователя.
3. Сохрани качество обычных страниц. Добавь случаи A4-подобного листа, двух листов, страницы внутри внешнего прямоугольного фона, узкого чека, тени, слабого контраста и документа у границы кадра.
4. Исправь отбор, если внешняя рамка систематически побеждает настоящий лист из-за одной площади. Не объявляй любой большой прямоугольник достоверным документом только по сумме геометрических бонусов.
5. Если кандидаты неоднозначны, безопасный результат — отказ от автоматической обрезки с возможностью ручной коррекции. Не угадывай объект ценой обрезанного содержания.
6. После `fitLine` и преобразований повторно проверяй конечный четырёхугольник: конечные числа, выпуклость, четыре разных угла, достаточная площадь, разумное отклонение от исходного кандидата. Независимый clamp координат не заменяет проверку геометрии.
7. Не обещай восстановление отсутствующих за кадром углов. Не обещай отличать документ от визуально идентичного прямоугольного объекта без дополнительной информации.

### Минимальный фиксированный набор

- Текущий сильный лист на тёмном фоне и однотонный фон из существующих тестов.
- Лист с видимыми четырьмя краями, занимающий 90%, 95% и 98% площади кадра.
- Чеки 1:4, 1:8, 1:12, вертикально и горизонтально. Длинная сторона занимает 70–90% кадра, короткая сторона детекторной копии не меньше 24 px.
- Лист с умеренной перспективой и поворотами около 45°.
- Лист внутри большего прямоугольного фона; два конкурирующих кандидата.
- Фон с полосами/текстовыми блоками без полноценного контура листа.

Для однозначных чистых синтетических положительных случаев: полный документ найден, polygon IoU с эталоном ≥ 0.90, максимальная ошибка угла ≤ 2% диагонали документа. Для шумных/неоднозначных случаев важнее отсутствие уверенно неверной обрезки; ожидаемый отказ допустим и фиксируется заранее в наборе.

Эти численные пороги относятся к синтетическим fixtures. Не переноси их как доказанную точность реальных фотографий. Не упрощай fixture после неудачного прогона ради зелёного результата; исправление ошибки самого эталона объясняй отдельно.

## 14. Официальные источники для геометрии CameraX

- [ViewPort](https://developer.android.com/reference/androidx/camera/core/ViewPort) — общий участок сенсора и различие crop metadata/сохранения файла.
- [ImageProxyTransformFactory](https://developer.android.com/reference/androidx/camera/view/transform/ImageProxyTransformFactory) — построение преобразования из ImageProxy; смысл crop/rotation flags проверять по фактическому контракту координат.
- [FileTransformFactory](https://developer.android.com/reference/androidx/camera/view/transform/FileTransformFactory) — преобразования для файла с учётом поддерживаемых метаданных.

Проверяй применимость API к используемой в проекте версии CameraX. Обновление библиотеки не является обязательным решением и требует отдельного технического основания.
