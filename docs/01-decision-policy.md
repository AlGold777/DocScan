# Decision Policy

**Document ID:** `01-decision-policy`  
**Purpose:** единая политика принятия, вывода, делегирования и эскалации решений при разработке продукта и системы.

---

# 1. Назначение

Этот документ определяет:

- какие решения модель может принимать самостоятельно;
- какие решения модель может только логически вывести;
- какие решения требуют продуктового выбора;
- какие требуют внешней проверки;
- какие должны оставаться пространством архитектурного решения;
- как оформлять принятые решения;
- как разрешать конфликты между источниками;
- как предотвращать скрытое добавление требований.

Политика применяется ко всем этапам:

- functional map;
- functional specification;
- product decisions;
- platform constraints;
- pre-architecture brief;
- architecture;
- architecture review;
- implementation planning.

---

# 2. Главный принцип

**Отсутствие решения не является разрешением модели придумать решение.**

Если решение нельзя:

1. найти в authoritative source;
2. однозначно вывести из уже принятых требований;
3. либо принять на основании явно делегированного полномочия,

оно остаётся открытым.

Industry practice, common sense, типичный UX и «обычно делают так» не являются достаточным основанием для продуктового правила.

---

# 3. Иерархия источников

При определении того, что уже решено, использовать следующий порядок приоритета.

## P1 — Explicit owner decision

Явно принятое решение владельца продукта / заказчика.

Примеры:

- прямое решение в текущем обсуждении;
- утверждённый Product Decision;
- явно подтверждённое изменение предыдущего решения.

Имеет высший приоритет.

---

## P2 — Approved product specification

Утверждённые документы:

- functional map;
- functional specification;
- product decisions;
- scope definition;
- product principles.

---

## P3 — Approved constraints

Подтверждённые:

- platform constraints;
- legal/regulatory constraints;
- security constraints;
- external system contracts.

---

## P4 — Derived consequence

Решение, которое однозначно следует из P1–P3.

Допускается только если альтернативное поведение нарушило бы существующее требование.

---

## P5 — Architecture decisions

Принятые архитектурные решения.

Они могут детализировать реализацию, но не могут изменять продуктовую семантику без отдельного Product Decision.

---

## P6 — Implementation decisions

Локальные решения реализации.

Имеют самый низкий нормативный приоритет.

---

# 4. Правило конфликта источников

Если два источника противоречат друг другу:

1. приоритет имеет источник более высокого уровня;
2. при равном уровне — более позднее явно принятое решение;
3. новое решение должно явно указывать, что оно заменяет предыдущее;
4. нельзя самостоятельно «синтезировать компромисс» между несовместимыми требованиями.

Если приоритет определить невозможно:

`CONFLICT — NEEDS RESOLUTION`

---

# 5. Классы решений

Каждый обнаруженный пробел должен быть отнесён ровно к одному классу.

---

## A — LOGICALLY DETERMINED

Решение однозначно следует из уже принятых требований.

### Модель может принять решение самостоятельно

Условия:

- существует только один вариант, совместимый со всеми authoritative requirements;
- альтернативный вариант нарушает хотя бы одно принятое правило или инвариант;
- не добавляется новое пользовательское предпочтение.

### Authority

`AUTH-A — Logical consequence`

### Результат

Создать `PD-*` со статусом `DECIDED`.

---

## B — DELEGATED LOW-RISK DECISION

Есть несколько допустимых вариантов, но выбор не изменяет существенную продуктовую семантику и явно делегирован модели этой политикой.

### Модель может выбрать вариант самостоятельно только если одновременно выполняются все условия

1. пользовательский результат остаётся тем же;
2. scope не расширяется;
3. новые обязательства продукта не возникают;
4. данные пользователя не теряются;
5. privacy/security/compliance не ухудшаются;
6. решение легко обратимо;
7. оно не создаёт существенный vendor/platform lock-in;
8. оно не влияет на публичный контракт системы;
9. цена ошибочного выбора невысока.

### Примеры

Допустимо выбрать:

- точное внутреннее имя состояния;
- порядок внутренних шагов без изменения observable behaviour;
- нейтральный fallback wording при уже определённой семантике;
- внутреннюю организацию документации.

### Нельзя использовать B для

- UX-поведения;
- default selection;
- destructive behaviour;
- retention;
- удаления данных;
- privacy;
- pricing;
- scope;
- пользовательских разрешений;
- файлового поведения;
- naming semantics;
- бизнес-правил;
- irreversible actions.

### Authority

`AUTH-B — Delegated low-risk choice`

---

## C — EXTERNAL FACT REQUIRED

Для решения требуется неизвестный внешний факт.

Примеры:

- поддерживает ли Android API конкретное поведение;
- существует ли системное ограничение;
- нормативное требование;
- ограничение стороннего SDK;
- поведение файловой системы;
- технический лимит устройства.

### Модель не принимает решение

Статус:

`NEEDS FACT`

### Resolution route

- найти authoritative source;
- провести эксперимент;
- проверить документацию;
- выполнить spike/prototype;
- получить подтверждение внешнего владельца системы.

---

## D — PRODUCT PREFERENCE REQUIRED

Существует несколько корректных пользовательских вариантов, и выбор зависит от желаемого поведения продукта.

Примеры:

- auto-select или manual select;
- confirmation dialog или immediate action;
- удалить оригинал или сохранить;
- какой default выбрать;
- как должен вести себя empty selection.

### Модель не выбирает

Статус:

`NEEDS PREFERENCE`

### Authority

Требуется решение Product Owner / владельца продукта.

---

## E — AUTHORITY REQUIRED

Решение имеет продуктовые или организационные последствия, но полномочия текущего процесса недостаточны.

Примеры:

- изменение scope;
- существенная privacy policy;
- monetization;
- юридически значимое поведение;
- обязательства перед внешними системами;
- изменение ранее утверждённого инварианта.

### Статус

`NEEDS AUTHORITY`

### Resolution route

Эскалировать владельцу соответствующего полномочия.

---

## F — ARCHITECTURAL DECISION

Существует несколько технически допустимых способов реализации, которые удовлетворяют одинаковому продуктовому контракту.

Примеры:

- Room или другой persistence layer;
- WorkManager / foreground service / собственная очередь;
- worker pool size;
- database schema;
- locking strategy;
- caching;
- retry implementation;
- compression algorithm;
- internal storage layout.

### Модель, пишущая functional specification, решение не принимает

Статус:

`ARCHITECTURAL OPEN QUESTION`

### Resolution route

Передать на этап architecture design.

---

# 6. Что считается продуктовым решением

Решение является продуктовым, если оно меняет хотя бы одно из следующего:

- что пользователь может сделать;
- что пользователь видит;
- когда действие доступно;
- что происходит после действия;
- какие пользовательские данные создаются, изменяются или удаляются;
- какое поведение является default;
- какие ограничения видит пользователь;
- какие ошибки и recovery доступны;
- какие данные сохраняются между сессиями;
- какие действия irreversible;
- composition/order/selection semantics;
- пользовательский lifecycle объекта.

Такие решения нельзя маскировать как архитектурные.

---

# 7. Что считается архитектурным решением

Решение является архитектурным, если при разных вариантах реализации:

- пользователь видит одинаковое поведение;
- входы и выходы capability не меняются;
- business rules не меняются;
- acceptance criteria остаются теми же;
- data-loss/security/privacy guarantees не меняются.

Если хотя бы одно из этих условий нарушается, вопрос уже не является чисто архитектурным.

---

# 8. Derived rules

Статус `DERIVED` разрешён только если вывод **логически неизбежен**.

Для каждого derived rule необходимо указать:

- исходные требования;
- логическую связь;
- почему альтернативное поведение им противоречит.

Запрещено использовать `DERIVED` для:

- предпочтительного UX;
- industry convention;
- более простой реализации;
- более дешёвой реализации;
- более красивого интерфейса;
- «разумного default».

---

# 9. Assumptions

Assumption не является решением.

Допустимый assumption:

- используется для продолжения анализа;
- явно обозначен;
- не превращается в Business Rule;
- имеет revision trigger.

Формат:

`ASSUMPTION | Basis | Impact | Validation route | Revision trigger`

Если assumption влияет на пользовательское поведение, capability не считается окончательно закрытой.

---

# 10. Defaults

Не использовать implicit defaults.

Default допустим только если:

1. он уже зафиксирован;
2. логически следует из существующего решения;
3. либо выбран через разрешённый `PD-*`.

Фраза:

> «если не указано иное, используем стандартное поведение»

запрещена без определения того, что именно является стандартным поведением.

---

# 11. Решения с высоким риском

Модель не должна самостоятельно принимать решения, связанные с:

- потерей пользовательских данных;
- destructive overwrite;
- irreversible actions;
- privacy;
- security;
- authentication/authorization;
- legal/compliance;
- financial consequences;
- изменение scope;
- изменение публичных API/contracts;
- retention пользовательских данных;
- background access к пользовательским данным;
- отправка данных за пределы устройства;
- автоматическое удаление данных.

Минимальный статус:

`NEEDS PREFERENCE`, `NEEDS AUTHORITY` или `NEEDS FACT`.

---

# 12. Reversibility

Для каждого PD оценить обратимость.

## LOW

Решение легко изменить без:

- migration;
- пользовательской потери данных;
- изменения контрактов;
- заметной переделки архитектуры.

## MEDIUM

Изменение требует ограниченной переработки или migration.

## HIGH

Изменение затрагивает:

- persistent data;
- публичный контракт;
- фундаментальную архитектуру;
- privacy/security model;
- пользовательские ожидания;
- существенный объём реализации.

Высоко необратимые решения требуют более сильного основания.

---

# 13. Правило минимального обязательства

Если для выполнения требований достаточно более слабого правила, не создавать более сильное.

Пример:

Требование:

> пользователь не должен потерять Page при crash.

Не следует автоматически превращать его в:

> вся обработка должна использовать WorkManager.

Первое — продуктовый invariant.

Второе — один из возможных архитектурных механизмов.

---

# 14. Scope control

Новая функция не может появляться как побочный результат детализации.

Любое новое пользовательское действие, состояние, режим или persistent object должно иметь:

- source requirement;
- derived basis;
- либо Product Decision.

Если capability требует нового scope:

`NEEDS AUTHORITY`

---

# 15. Error handling policy

Ошибка не является разрешением придумать recovery flow.

Если recovery уже определён — использовать его.

Если нет:

- пользовательски значимый recovery → `NEEDS PREFERENCE`;
- чисто технический механизм восстановления при сохранении того же UX → `ARCHITECTURAL OPEN QUESTION`.

---

# 16. Product Decision record

Каждое принятое A/B решение оформляется как `PD-*`.

Формат:

| Field | Value |
|---|---|
| PD ID | `PD-XXX` |
| Status | `DECIDED / SUPERSEDED` |
| Question | Что решается |
| Classification | A / B |
| Alternatives | Реальные альтернативы |
| Chosen option | Выбранное решение |
| Decision basis | Requirement IDs + version |
| Authority basis | `AUTH-A` / `AUTH-B` / explicit authority |
| Assumptions | Если есть |
| Consequences | Новые правила и ограничения |
| Affects | Capability / BR / AC |
| Reversibility | LOW / MEDIUM / HIGH |
| Revision trigger | Условие пересмотра |
| Supersedes | Previous PD, если применимо |

---

# 17. Authority Rules

## AUTH-A — Logical consequence

Модель может принять решение, если оно является единственным вариантом, совместимым с уже принятыми требованиями.

---

## AUTH-B — Delegated low-risk choice

Модель может принять низкорисковое, обратимое решение, не меняющее продуктовую семантику.

---

## AUTH-C — External verification required

Модель не имеет полномочий заменять неизвестный внешний факт предположением.

---

## AUTH-D — Product owner decision

Любой новый пользовательский preference/default требует Product Owner.

---

## AUTH-E — Scope / policy authority

Решения, меняющие scope, privacy, security, compliance, irreversible data behaviour или существенные обязательства системы, требуют явного владельца полномочия.

---

## AUTH-F — Architecture ownership

Выбор технического механизма, не меняющего продуктовый контракт, принадлежит архитектурному этапу.

---

# 18. Решение конфликтов между Product и Architecture

Архитектура обязана реализовывать утверждённый продуктовый контракт.

Архитектурное решение не может:

- ослабить Business Rule;
- изменить observable behaviour;
- silently remove edge case;
- изменить lifecycle;
- заменить explicit product decision более удобной реализацией.

Если продуктовый контракт технически невозможен или чрезмерно дорог:

архитектор создаёт:

`ARCHITECTURE CONSTRAINT / PRODUCT IMPACT`

и возвращает вопрос на Product Decision.

Он не меняет продукт самостоятельно.

---

# 19. Revision policy

Решение можно пересматривать только при наличии revision trigger.

Типичные triggers:

- новое требование;
- новый platform fact;
- architecture constraint;
- security finding;
- usability evidence;
- change of scope;
- contradiction discovered;
- performance limit confirmed.

При изменении решения:

1. старый PD получает `SUPERSEDED`;
2. создаётся новый PD;
3. обновляются связанные BR/AC;
4. сохраняется traceability.

---

# 20. Запрещённые основания для решений

Нельзя принимать Business Decision только потому, что:

- «так обычно делают»;
- «пользователь, вероятно, ожидает»;
- «так проще разработать»;
- «так красивее»;
- «так делают конкуренты»;
- «Android обычно работает так»;
- «это best practice»;
- «так модель считает удобнее».

Это может быть аргументом при обсуждении вариантов, но не authority basis.

---

# 21. Правило uncertainty

Если уверенность недостаточна:

**не выбирать более вероятный вариант.**

Использовать:

- `NEEDS FACT`;
- `NEEDS PREFERENCE`;
- `NEEDS AUTHORITY`;
- `ARCHITECTURAL OPEN QUESTION`;
- `CONFLICT — NEEDS RESOLUTION`.

Ложная определённость хуже явного open question.

---

# 22. Gate Check

Перед утверждением любого specification/brief выполнить проверку.

### G1 — Hidden decisions

Есть ли правило без authoritative source или PD?

Норма:

`NONE`

### G2 — Unauthorized product choices

Есть ли D/E, которые модель закрыла самостоятельно?

Норма:

`NONE`

### G3 — Architecture leakage

Есть ли F, зафиксированные как обязательный Business Rule без необходимости?

Норма:

`NONE`

### G4 — Unresolved conflicts

Есть ли несовместимые действующие требования?

Норма:

`NONE`

### G5 — Traceability

Можно ли для каждого обязательного правила определить:

`Source → Decision → Rule → Acceptance Criterion`

Норма:

`PASS`

### G6 — Scope creep

Появились ли новые capability/actions/states без основания?

Норма:

`NONE`

### G7 — Assumptions

Есть ли assumption, скрыто превращённый в requirement?

Норма:

`NONE`

---

# 23. Decision Summary Format

В конце каждого этапа выводить:

| Status | Count |
|---|---:|
| Logically determined | N |
| Delegated decisions | N |
| Needs fact | N |
| Needs preference | N |
| Needs authority | N |
| Architectural open questions | N |
| Conflicts | N |

И отдельным блоком:

**Blocking decisions**

Только вопросы, без закрытия которых невозможно однозначно продолжить следующий этап.

---

# 24. Fundamental rule

Главная обязанность модели — не максимизировать количество принятых решений.

Главная обязанность модели — **максимизировать определённость системы при минимальном количестве необоснованных решений**.

Хорошая спецификация содержит не ноль открытых вопросов.

Хорошая спецификация содержит **только действительно открытые вопросы**, а все остальные требования имеют доказуемое происхождение.
